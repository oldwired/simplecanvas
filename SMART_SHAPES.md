# Smart Shapes — scripting reference

A **smart shape** is a Shape Library item whose visible content is generated by a small
JavaScript script you write, instead of being fixed geometry. The container itself never
draws a box — it's a plain, styleable item (Fill/Stroke/Stroke-width/Text-color/Font all work
on it normally), and your script decides which of the shapes it generates ("children") use
that styling. Built-in examples: an analog clock, a block arrow, a bar chart, a countdown
timer.

This file is a reference for **writing** a smart shape's script — by hand, or by handing this
file to an AI assistant along with a description of what you want. It does not cover using the
app as an end user; see [README.md](README.md) for that.

## Quick start

1. Open the **Shape Library** panel → **Manage** → **Add smart shape…**.
2. Pick a starting point from the **Template** dropdown (Clock / Arrow / Arc / Timer / Chart /
   Minimal / Blank), or just start typing your own script over it.
3. Give it a name and click **Add**. The new shape appears in the library, ready to place.
4. On the canvas, double-click a placed smart shape to enter its **edit mode** (solid blue
   corner markers) — drag its handles there to change its state. Double-click again, or click
   outside it, to leave.

The **script** field takes a single JavaScript **expression** — not a series of statements —
that evaluates to one object literal: `({ children(state, style, w, h){ ... }, ... })`. It's
compiled with `new Function('"use strict";return (' + yourScript + ');')()`, so:

- Wrap it in parentheses if you paste it as a bare object literal (`{...}` on its own is parsed
  as a block, not an object) — every template already does this (`` `({ ... })` ``).
- No `import`/`export`, no top-level `let`/`const`/`function` declarations outside the object
  literal. Helper functions are fine as **methods** on the object (see `_layout()` in the Timer
  template) — the app always calls your hooks as `def.hookName(...)`, so `this` inside a method
  correctly refers to your own script object.
- The only thing your script ever gets handed is plain, already-computed data (state, style,
  width, height, pointer coordinates) — never `ctx`, `document`, or any other app internal.

## The script object

Only `children()` is required. Everything else is optional and only needed if your shape has
its own interactive state.

| Hook | Called | Arguments | Returns |
|---|---|---|---|
| `initState()` | Once, when a fresh instance is placed/created | — | a plain, JSON-safe state object |
| `initStyle()` | Once, when a fresh instance is created (right after `initState()`) | — | a partial style/size override (see below) |
| `children(state, style, w, h, editing)` | Every render | current state, resolved style, container width/height, `true` only for the one instance currently in edit mode | array of child shape descriptors |
| `handles(state, w, h, style)` | While in edit mode, to draw handle markers | state, width/height, resolved style | array of `{id, x, y, kind?}` |
| `hitEdit(state, lx, ly, w, h, style)` | On press, while in edit mode | state, press position (**local** coords, see below), width/height, resolved style | a handle `id`, or `null`/falsy if the press missed every handle |
| `dragEdit(state, handle, lx, ly, w, h, style)` | While dragging a handle (continuously), and once on a zero-movement click | state, the `id` returned by `hitEdit`, current pointer position (local coords), width/height, resolved style | the **new** state object |

State is never mutated in place — `dragEdit` returns a fresh object (`{...state, ...}` is the
usual pattern), which the app assigns back and pushes onto the undo stack.

Every hook call is wrapped in `try/catch` by the app. A throwing or missing hook never crashes
the canvas — worst case, `children()` returning `[]` (or throwing) just means the container
renders nothing visible that frame.

### `initState()`

Returns the state your shape starts with. Called once per placement; `w`/`h` aren't decided
yet at this point, so state can't depend on them (the Minimal template's radius, for example, is
a plain tuned literal, not a fraction of the box).

```js
initState(){ return { value: -45 }; }
```

### `initStyle()` (optional)

Lets a script override some of the *creation-time* style/size the toolbar would otherwise
supply, without needing to touch anything after placement. Return a partial object; any field
you omit keeps the normal default. Recognized fields, each individually validated (an
unknown/wrong-typed field is just ignored, not rejected):

| Field | Clamp |
|---|---|
| `color`, `fillColor`, `textColor` | must be a valid CSS color string |
| `fill`, `strokeOn` | boolean |
| `size` | 1–60 |
| `fontFamily` | must be one of the app's known font families |
| `fontSize` | 6–400, rounded |
| `w`, `h` | 20–2000, rounded |

Every field is still fully adjustable afterward via the ordinary toolbar/resize handles —
`initStyle()` only ever affects the single moment of creation. Example (the Chart template):

```js
initStyle(){ return { fontSize: 12, strokeOn: false, w: 240, h: 160 }; }
```

Without an `initStyle()`, a new instance starts black, unfilled, stroke on, at 180×180, using
whatever font/fill-color/text-color the toolbar currently has.

### `children(state, style, w, h, editing)` (required)

Returns an array of plain **child shape descriptors** — the actual visible content. These are
**never stored**; they're recomputed fresh every render from the container's current
`x/y/w/h/state`. See [Child descriptors](#child-descriptors) below for their shape.

`editing` is `true` only for the one instance currently in interactive edit mode (by identity,
not type) — `false`/`undefined` otherwise, including during PNG/SVG/HTML export. Use it to draw
edit-only chrome (an add/delete control, say) that should never appear in a committed render or
an export.

### `handles(state, w, h, style)` (optional)

Returns `[{id, x, y, kind}, ...]` — one entry per point `hitEdit`/`dragEdit` can grab, in the
same **local** coordinate frame as `children()` (container's own top-left as origin). Without
this, edit mode gives no visual clue *where* to drag, only *that* you're in edit mode (the 4
corner markers alone). The app draws a small solid-blue dot at each reported point.

`kind` is optional, defaulting to `'drag'` (a continuous drag point, like a resize handle).
Mark it `'click'` for a discrete, one-shot action — an add/delete button, a toggle — rather than
something meant to be dragged around:

```js
handles(state, w, h){
  return [
    { id:'hand', x: cx + Math.sin(a)*r, y: cy - Math.cos(a)*r },   // 'drag' (default)
    { id:'add', x: addBtnX, y: addBtnY, kind:'click' },
  ];
}
```

Without `kind:'click'`, a handle representing an action has a real bug waiting: any actual
press-and-release fires several pointermove events even with no visible movement, so
`dragEdit` would run once per event instead of once per click (e.g. inserting several new bars
from what looked like a single tap on "+"). `kind:'click'` makes the app resolve it exactly
once, from the original press position, on release.

### `hitEdit(state, lx, ly, w, h, style)` (optional, needed if you have handles)

Given a press position, return the `id` of the handle it landed on (within your own chosen hit
radius), or `null`/falsy if it missed everything. **Coordinates are already local** — `(0,0)` is
the container's own top-left, same frame as `children()`, **not** the same convention `toLocal`
uses elsewhere in the app (which only undoes rotation, not translation) — the app subtracts
`it.x`/`it.y` for you before calling this.

```js
hitEdit(state, lx, ly, w, h){
  return Math.hypot(lx - handX, ly - handY) < 14 ? 'hand' : null;
}
```

### `dragEdit(state, handle, lx, ly, w, h, style)` (optional, needed if you have handles)

Given the `id` `hitEdit` returned and the current (local) pointer position, return the new
state. Called continuously while dragging a `'drag'`-kind handle, or exactly once (from the
original press position) for a `'click'`-kind handle or a zero-movement click.

```js
dragEdit(state, handle, lx, ly, w, h){
  if(handle !== 'r') return state;
  const maxR = Math.min(w, h) / 2;
  return { ...state, r: Math.max(5, Math.min(maxR, Math.hypot(lx - w/2, ly - h/2))) };
}
```

For a `'click'`-kind handle, or an ordinary drag-kind handle pressed and released with zero
movement, a history entry (undo step) is only pushed if the returned state actually differs
from the current one (compared via `JSON.stringify`) — re-clicking something that lands back on
its own current value doesn't create a no-op undo entry. A real drag with movement always
commits on release, regardless of the net state change.

## The `style` object

Passed to every hook that takes a `style` argument — the container's own **currently resolved**
style, exactly what the toolbar's Fill/Stroke/Stroke-width/Text-color/Font controls currently
show for this instance:

| Field | Meaning |
|---|---|
| `color` | stroke/line color |
| `fillColor` | fill color |
| `fill` | boolean — is Fill on |
| `strokeOn` | boolean — is Stroke on |
| `textColor` | text color |
| `size` | stroke width |
| `dash` | dash pattern |
| `fontFamily`, `fontSize`, `font` | the container's own font settings (`font` is the ready-to-use CSS font string) |
| `presetColors` | the toolbar's own color-swatch palette, as an array of hex strings, in its declared display order |

Use `presetColors` instead of a hard-coded color list/count whenever your shape's design
depends on "however many colors the toolbar actually offers" (the Chart template sizes its max
bar count off this, so it never silently drifts out of sync with the real palette).

## Child descriptors

Each entry `children()` returns is a plain object describing one shape, in **local
coordinates** — `(0,0)` is the container's own top-left, `(w,h)` its bottom-right. The app
shifts every child into world coordinates for you; never add the container's own `x`/`y`
yourself.

Supported `type`s and their own fields (identical to a normal, top-level item of that type):

- **`rect`** / **`ellipse`**: `{type, x, y, w, h, color, fillColor, fill, strokeOn, size, dash}`
- **`line`**: `{type, x1, y1, x2, y2, color, size, dash}`
- **`text`**: `{type, x, y, w, h, text, font, color, textColor, align, fill, strokeOn}` —
  `align` is `'left'`/`'center'`/`'right'`. A label that shouldn't draw its own box needs
  `strokeOn:false, fill:false` explicitly — the `text` type's own default is "box on unless
  told off."
- **`polygon`**: `{type, points, closed, color, fill, fillColor, strokeOn}` — `points` is an
  array of `{x, y}` (see [Arcs](#arcs-in-a-polygon-child) below for curved segments).

### Style inheritance — read this before your shape renders invisible

Only `color`, `textColor`, `size`, and `dash` are inherited onto a child **automatically** — a
child descriptor that omits them gets the container's own current value for free. **`fill`,
`fillColor`, and `strokeOn` are deliberately *not* auto-inherited.** Reference `style.fill`,
`style.fillColor`, `style.strokeOn` explicitly on any child you want to follow the toolbar's own
Fill/Stroke toggles:

```js
children(state, style, w, h){
  return [{
    type:'ellipse', x:0, y:0, w, h,
    color: style.color, size: style.size,          // inherited anyway, but explicit is fine too
    fill: style.fill, fillColor: style.fillColor,   // must be explicit
    strokeOn: style.strokeOn,                        // must be explicit
  }];
}
```

Why: `strokeOn` means something different per type — for a `rect`/`ellipse` it's "show an
outline," but for a `line` it's "is this visible **at all**." A container's everyday
`strokeOn:false` (its own box is invisible by design) would silently make every `line` child
invisible too if it were auto-inherited. A **hard-coded** child (Clock's face outline, say,
which is meant to always be visible) simply never reads `style.strokeOn` at all.

### Your shape is responsible for its own bounds

Children are **never clipped** to the container box — `w`/`h` are just numbers your script
receives, not an enforced boundary. Keep any interactive geometry (a draggable radius, an
adjustable ratio) a function of `w`/`h`, clamped on **both** ends in `dragEdit`, or it can grow
past the container's own selection rectangle:

```js
dragEdit(state, handle, lx, ly, w, h){
  const maxR = Math.min(w, h) / 2;                              // upper bound: never past the box
  const r = Math.max(5, Math.min(maxR, Math.hypot(lx-w/2, ly-h/2)));  // lower bound: never degenerate
  return { ...state, r };
}
```

## Arcs in a polygon child

A `polygon` point may carry an optional `arcTo: {cx, cy, r, a1, a2}` — "the segment **leaving**
this point is a circular arc to the next point, not a straight line." Angle convention: `0` is
straight up (12 o'clock), increasing **clockwise** — the same convention a clock hand's own
angle math uses, *not* canvas/SVG's native 0-is-3-o'clock convention (the app converts at the
render/export boundary; your script never needs to think about it).

Sketched as a standalone helper below for clarity — in a real script this logic lives as a
`children()`-only local step (or a method on your own script object, like Timer's `_layout()`),
since only the top-level object literal itself is a valid script:

```js
// A filled pie wedge from angle a1 to angle a2, radius r, centered at (cx, cy):
function wedge(cx, cy, r, a1, a2, style){
  const start = { x: cx + r*Math.sin(a1), y: cy - r*Math.cos(a1), arcTo: { cx, cy, r, a1, a2 } };
  const end   = { x: cx + r*Math.sin(a2), y: cy - r*Math.cos(a2) };
  return {
    type:'polygon', closed:true, fill:true, strokeOn:false,
    color: style.fillColor, fillColor: style.fillColor,
    points: [ {x:cx, y:cy}, start, end ],   // center -> arc start -> (arc) -> arc end -> back to center
  };
}

// The bow alone (no center point, not filled): drop the center point and set closed:false --
// points: [ start, end ], closed:false
```

A closed `[center, arcStart(with arcTo), arcEnd]` triple draws a genuine pie wedge (`M → L → A →
L → Z`); dropping the center point and `closed:false` draws just the bow itself. Both the Arc
and Timer templates use this. If your sweep can reach a **full turn** (2π), clamp it a hair
short (`Math.min(sweep, 2*Math.PI - 0.0001)`) — SVG's arc command can't represent an exact full
circle (start and end coincide), which would otherwise break your shape's own SVG/HTML export
even though it renders fine on canvas.

## Constraints

- **Script length**: 50,000 characters. **State**: 4,000 characters once `JSON.stringify`'d.
  Both are enforced on save/load — an oversized script or state is silently rejected (the item
  fails to load) rather than truncated. 50,000 comfortably fits an entire reference template file,
  explanatory header comment included, the way "A complete worked example" below tells you to
  paste one — the longest shipped one (`race-start-timer.js`) is already ~37,300 characters.
- **Sandboxed.** A smart shape's script is real JavaScript, but it never runs in the page's own
  scope — every hook (`children`/`handles`/`hitEdit`/`dragEdit`/`initState`/`initStyle`) is
  called inside a single, shared, dedicated Worker with `fetch`/`XMLHttpRequest`/`WebSocket`/
  `importScripts`/`Worker`/`indexedDB`/`caches`/`BroadcastChannel`/`Notification` all deleted
  before any script runs in it. A Worker has no `document`/`window`/DOM and no
  `localStorage`/cookies at all (not exposed in worker scope, regardless of origin), so none of
  those are reachable either way. Every call crosses `postMessage` and is therefore async; the
  app bridges that with a last-known-good cache for live rendering and a real await for export —
  a script's own hooks don't need to know or care about this. An infinite loop in a script hangs
  only that shared worker (never the page's own main thread), is caught by a timeout, and the
  worker is torn down and recreated — the worst a hostile or broken script can do is make every
  smart shape go temporarily blank for a few seconds (scripts aren't isolated from EACH OTHER,
  only from the host page and your data), never crash or freeze the app, and never reach
  anything outside the worker it runs in.
- Compiled once per distinct script string and cached (inside the sandbox, not the page) —
  editing a script's text (even by one character) recompiles it; identical text across
  different items reuses the same compiled function.
- Untested and not recommended as children: nesting another smart shape, a table, or an image —
  the rendering pipeline doesn't forbid them, but no shipped template uses them and they haven't
  been exercised. Stick to `rect`/`ellipse`/`line`/`text`/`polygon`.

## A complete worked example

The **Minimal** template (in the app's own template picker) — a circle with one draggable
radius handle. Short enough to read end to end; a good starting skeleton for a new shape with
exactly one piece of interactive state:

```js
({
  // The only state this object needs: its own radius.
  initState(){ return { r: 45 }; },

  // One child: a circle centered in the box, fully following the container's own style.
  children(state, style, w, h){
    return [{
      type:'ellipse', x:w/2-state.r, y:h/2-state.r, w:state.r*2, h:state.r*2,
      color: style.color, size: style.size, strokeOn: style.strokeOn,
      fill: style.fill, fillColor: style.fillColor,
    }];
  },

  // One handle, on the circle's own right edge -- same point handles() reports and hitEdit checks.
  handles(state, w, h){ return [{ id:'r', x: w/2+state.r, y: h/2 }]; },

  hitEdit(state, lx, ly, w, h){
    const near = Math.hypot(lx-(w/2+state.r), ly-h/2) < 12;
    return near ? 'r' : null;
  },

  // Clamped both ways: never smaller than 5px, never bigger than half the container's own box.
  dragEdit(state, handle, lx, ly, w, h){
    if(handle !== 'r') return state;
    const maxR = Math.min(w, h) / 2;
    const r = Math.max(5, Math.min(maxR, Math.hypot(lx-w/2, ly-h/2)));
    return { ...state, r };
  },
})
```

## Shipped reference templates

Look at whichever is closest to what you want and adapt it — pick it from the **Template**
dropdown to load its full source into the script field.

| Template | Demonstrates |
|---|---|
| **Clock** | Multiple children (face, 12 ticks, 2 hands); selective style hard-coding — the face follows Fill, but ticks/hands only follow Stroke, never Fill |
| **Arrow** | A single filled `polygon` child; *full* style inheritance (nothing hard-coded) |
| **Arc** | Two independent drag handles sweeping a circular arc; the `arcTo` mechanism, fill-on-vs-off toggling a wedge vs. a bare bow |
| **Timer** | A shared `_layout()` helper method reused by `children()`/`handles()`/`hitEdit()` so derived geometry can't drift out of sync; a fixed-then-toolbar-driven color history; the full-turn SVG-arc clamp |
| **Chart** | Editable item *count* (not just values) via `kind:'click'` add/delete handles; `editing`-only chrome; sizing off `style.presetColors` |
| **Minimal** | The smallest complete interactive example — see above |
| **Blank** | `{initState(){return{};}, children(){return[];}}` — an empty starting point |

## Asking an AI to write one for you

Paste this file (or its relevant sections) as context, then describe the shape you want,
including: what it should look like, what single piece of state (if any) it should carry, what
should be draggable, and whether it should follow the toolbar's own Fill/Stroke colors or use
fixed colors of its own. Ask explicitly for the output to be **one script**, in the exact object
literal form these templates use — not a set of instructions, not a diff, not wrapped in a
`<script>` tag — since that's the only thing that pastes directly into the Script field.
